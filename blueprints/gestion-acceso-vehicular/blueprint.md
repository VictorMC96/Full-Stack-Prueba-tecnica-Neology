## 1. Project Overview & Non-Goals

### Vision

Sistema web para operar el acceso de vehículos a un estacionamiento: el personal de caseta registra
entradas y salidas por placa, el sistema calcula el cobro según el tipo de vehículo (oficial no paga,
residente acumula $0.05/min y se cobra en el informe mensual, no residente paga $0.50/min al salir) y
genera el informe de pagos de residentes en pantalla y como Excel. Al cerrar el mes se inicia un
periodo nuevo: los acumulados vuelven a cero y el historial queda archivado por periodo.

Es la prueba técnica Full Stack de Neology (tiempo estimado: 5 horas). Tiene dos lectores: el
operador que usa la interfaz y el evaluador técnico que clona el repositorio, sigue el README y juzga
calidad de código, organización, detalle de las interfaces y precisión frente al enunciado. Por eso
el alcance obligatorio del enunciado va siempre antes que cualquier extra.

### Users

| Persona | What they come to do | Frequency |
|---|---|---|
| Operador de caseta | Registrar entrada y salida por placa y ver el importe a cobrar | Decenas de veces al día |
| Administrador del estacionamiento | Dar de alta oficiales y residentes, consultar el listado y el detalle de un vehículo, generar el informe de pagos, iniciar el mes | Semanal / mensual |
| Evaluador técnico de Neology | Clonar, levantar backend y frontend con el README, ejecutar pruebas, revisar código y capturas | Una vez |

### Goals — v1 scope

1. El sistema registra altas de vehículos oficiales, residentes y no residentes por placa normalizada, y reclasifica un no residente cuando se da de alta como oficial o residente.
2. El sistema registra entradas y salidas con fecha y hora del servidor, impide dos estancias abiertas para una misma placa y calcula minutos completos e importe por tipo con el patrón Strategy.
3. El sistema genera el informe de pagos de residentes del periodo activo en JSON y en Excel (`.xlsx`) según la cabecera `Accept`.
4. El sistema inicia un mes nuevo archivando el periodo anterior sin borrar estancias y reiniciando los acumulados.
5. La interfaz Angular ofrece listado de vehículos paginado, ordenable y filtrable en servidor, formularios de operación validados, detalle por vehículo y página de reporte con descarga de Excel.
6. El repositorio entrega README en español, base de datos precargada, Swagger UI, pruebas automatizadas de backend y frontend, CI y capturas de pantalla.

### Non-Goals — explicitly out of scope for v1

| Not building | Why not now | Revisit when |
|---|---|---|
| Login, roles y bitácora de auditoría | El enunciado no pide cuentas; añadir seguridad consume la quinta parte del tiempo y abre una superficie que el evaluador no califica | El sistema se exponga fuera de la red de la caseta o haya más de un rol operativo |
| Docker y despliegue a un host | La entrega es un repositorio que se levanta en local con dos comandos; Docker no está instalado en la máquina de construcción | Se pida una URL pública o un entorno compartido |
| Base de datos persistente (H2 en archivo o PostgreSQL) | El enunciado fija H2 en memoria; los datos se precargan con Flyway en cada arranque | Los datos deban sobrevivir un reinicio |
| Tema oscuro | Un solo tema claro bien contrastado cabe en el tiempo; dos temas duplican la verificación de contraste | El operador trabaje en turnos nocturnos y lo pida |
| i18n multi-idioma | La interfaz es solo en español; externalizar textos no aporta a la evaluación | Exista un segundo idioma requerido |
| Tiempo real / WebSocket | El listado se refresca tras cada operación y a petición; ningún flujo se rompe sin push | Dos casetas operen en simultáneo y necesiten ver el mismo estado al instante |
| Lombok | Opcional en el enunciado; los `record` de Java 21 cubren DTOs y value objects sin procesador de anotaciones | Nunca para DTOs; solo si aparecen entidades mutables con mucho boilerplate |
| Tarifas editables desde la interfaz | Las tarifas viven en `application.yml`; una pantalla de configuración exige validación, permisos e historial | El negocio cambie tarifas con frecuencia |
| Multi-estacionamiento | Un solo estacionamiento; una columna de sede reescribe cada consulta | Se sume una segunda sede |
| Signal Forms | API nueva en Angular 22; los Reactive Forms son la opción estable que el enunciado evalúa ("validación de campos") | Signal Forms deje de ser experimental y el equipo lo adopte |
| Pruebas E2E con Playwright | Las pruebas Karma + integración backend ya cubren las reglas; E2E no cabe en 5 horas | Sobre tiempo tras el paso 15, o el proyecto continúe después de la entrega |

**The builder must not implement anything in this table**, aunque parezca un añadido pequeño junto
a un paso adyacente. Si un paso parece requerir un non-goal, es un defecto del blueprint: detenerse
y reportarlo en vez de ampliar el alcance.

## 2. Tech Stack

**Runtime track: ninguno de la base de conocimiento.** Esta es la desviación declarada: la base de
conocimiento de The Architect solo trae tracks para TypeScript/Node, Python, Go y Rails/Laravel, y el
enunciado fija **Angular + Spring Boot**. Por tanto no hay track de respaldo: cada pin de §11 viene
del informe verificado de `stack-researcher` de esta sesión (2026-09-30) y de ningún otro lugar. De
los archivos de capacidades (`database`, `api-design`, `frontend-architecture`, `styling`,
`accessibility`, `testing`, `deployment`) se toman solo las reglas transferibles, no sus comandos.

Esta tabla nombra *elecciones*, no versiones. Todos los pines viven en §11.

| Layer | Choice | Why this, over what |
|---|---|---|
| Language / runtime (backend) | Java 21 (LTS) | Es el JDK instalado en la máquina de construcción y cumple "Java 17+"; se descarta Java 25 porque obligaría a instalar otro JDK sin beneficio para la prueba |
| Framework (backend) | Spring Boot 4.1 con `spring-boot-starter-webmvc` | El enunciado dice "Spring Boot 3.x", pero Spring Initializr ya no ofrece 3.x y esa línea no tiene soporte OSS; se usa la línea estable vigente y se documenta en `docs/decisiones.md`. Se descarta WebFlux: no hay carga reactiva que lo justifique |
| Language / framework (frontend) | Angular 22 standalone + TypeScript, zoneless, control flow `@if`/`@for` | Cumple "Angular 16+" con la versión `latest`; standalone elimina NgModules. Se descarta Angular 16 literal por estar fuera de soporte |
| Styling | SCSS + theming Material 3 (`mat.theme`) + tokens como CSS custom properties | El enunciado pide SCSS o CSS y Angular Material; se descarta Tailwind porque mezclar dos mecanismos de estilo sobre Material rompe el sistema de diseño |
| Component layer | Angular Material + CDK | Pedido explícitamente; trae tabla, paginador, orden, diálogo y snackbar accesibles, que son el 90 % de esta interfaz |
| Database | H2 en memoria | Fijado por el enunciado. Se descarta H2 en archivo: no se pide persistencia y complica el arranque limpio del evaluador |
| ORM / data access | Hibernate + Spring Data JPA, esquema gobernado por Flyway (`ddl-auto=validate`) | El enunciado pide Hibernate + JPA; Flyway da esquema versionado y datos precargados reproducibles. Se descarta `ddl-auto=create` + `data.sql`: no valida el mapeo y oculta errores de esquema |
| Auth | NOT APPLICABLE — sin autenticación | El enunciado no define usuarios |
| Background work | NOT APPLICABLE — no hay trabajo asíncrono | Todas las operaciones son petición/respuesta de milisegundos |
| Payments | NOT APPLICABLE | El "cobro" es un cálculo mostrado al operador, no un pago procesado |
| File storage | NOT APPLICABLE | El Excel se genera en memoria con Apache POI y se transmite en la respuesta |
| Email / notifications | NOT APPLICABLE | El resultado de cada operación se muestra con `MatSnackBar` |
| API docs | springdoc-openapi (Swagger UI) | "Swagger (opcional)" en el enunciado; cuesta una dependencia y le da al evaluador una consola para probar |
| Tests | JUnit Jupiter + Mockito + AssertJ (backend); Jasmine + Karma con ChromeHeadless (frontend) | Karma es lo que el enunciado nombra; en Angular 22 no es el runner por defecto, por eso se pide con `--test-runner=karma` |
| Formato | Spotless con google-java-format (backend); Prettier (frontend) | Un formateador por lenguaje, verificado en la puerta; se descarta Checkstyle por el tiempo de configuración |
| Hosting | Ninguno — ejecución local; CI en GitHub Actions | La entrega es una rama en GitHub, no un despliegue |
| Build / package manager | Maven Wrapper (`./mvnw`) y npm | Maven lo fija el enunciado y no está instalado globalmente, así que el wrapper es la única vía; npm viene con Node |

### Compatibility check

Checked against `knowledge/stack-compatibility.md` — ninguna de las filas de combinaciones
conocidas como malas aplica a este stack: un solo mecanismo de estilo (SCSS + Material, sin CSS-in-JS
ni utilidades), sin proveedor de identidad, un solo sistema de migraciones (Flyway; Hibernate solo
valida), base relacional con ORM SQL, REST simple sin capa de grafo, y un único framework HTTP por
proceso. La fila "framework de UI + otra major del runtime de componentes" se evita fijando Angular
Material y CDK en la misma major que Angular (§11).

Trampas propias de este stack que el constructor debe respetar (no provienen de esa tabla):

- **Spring Boot 4:** el starter web es `spring-boot-starter-webmvc`; en pruebas se usa `@MockitoBean`
  (nunca `@MockBean`); Jackson 3 vive en `tools.jackson.*`, por lo que se evita usar `ObjectMapper`
  directamente y se prefiere MockMvc con `jsonPath`.
- **Angular 22:** zoneless por defecto — en pruebas se espera con `await fixture.whenStable()`;
  `fakeAsync`/`tick` no están disponibles sin zone.js, así que los temporizadores (el `debounce` del
  filtro) se controlan con `jasmine.clock()`; formularios con Reactive Forms.
- **H2:** no soporta índices únicos parciales; las dos invariantes de unicidad condicional se
  resuelven con columnas anulables únicas (§4).

**Origen de cada archivo.** Todo archivo de este árbol tiene exactamente un origen: (a) un paso de §9
lo crea y lo nombra en su lista **Do**; (b) se emite como archivo real bajo `workspace/` y llega con
la copia de §10; o (c) lo genera un scaffolder ejecutado en §10 (`backend/**` por Spring Initializr,
`frontend/**` por `ng new`). **Nada bajo `workspace/` apunta a `backend/` ni a `frontend/`:** `ng
new` rechaza un directorio no vacío, así que esos dos directorios los crean los scaffolders y los
manifiestos `backend/pom.xml` y `frontend/package.json` son de su autoría; el blueprint solo describe
ediciones encima (pasos 2, 8 y 9).

**Boundary rules**

- `domain` no importa nada fuera de `java.*`: ni Spring, ni JPA, ni Jackson. `application` importa
  solo `domain` y `java.*`. Se verifica con `grep` en cada puerta de backend desde el paso 3.
- `infrastructure` implementa los puertos de `application`; es el único lugar con `jakarta.persistence`,
  `org.apache.poi` y `@ConfigurationProperties`.
- `web` llama a casos de uso de `application`; nunca a repositorios Spring Data ni a entidades JPA.
  Las entidades JPA nunca salen de `infrastructure.persistencia`.
- Ningún servicio ni caso de uso contiene `if`/`switch` sobre `TipoVehiculo`: el cobro se resuelve
  solo por `CalculadoraCobro`.
- Frontend: `features/*` importa de `core` y `shared`; `core` y `shared` no importan de `features`;
  una feature no importa de otra feature. Solo `core/api/*` usa `HttpClient`.
- Frontend: ningún archivo de componente contiene un color hexadecimal; los colores salen de los
  tokens de `styles.scss`.

**Convención de resolución de módulos.** Frontend: imports relativos, sin alias de rutas (`paths` en
`tsconfig` no se usa). Backend: paquetes Java bajo `mx.neology.acceso`. La reconciliación contra cada
cargador está en la matriz de §19.6.

## 4. Data Model

Cuatro tablas. Nombres en plural y `snake_case`, ids `UUID` generados en Java con
`UUID.randomUUID()`, marcas de tiempo `TIMESTAMP WITH TIME ZONE` asignadas por el servidor con el
`Clock` inyectado.

### Entities

**`periodos`** — un mes operativo. Nace al iniciar mes (o en la precarga), se cierra al iniciar el siguiente.

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `id` | UUID | PK | |
| `inicio` | TIMESTAMP WITH TIME ZONE | not null | Momento en que se abrió el periodo |
| `fin` | TIMESTAMP WITH TIME ZONE | null | `null` mientras está activo; se fija al iniciar el mes siguiente |
| `activo` | BOOLEAN | null, check `activo = TRUE`, unique | `TRUE` = periodo activo; `NULL` = cerrado. Nunca `FALSE` |
| `created_at`, `updated_at` | TIMESTAMP WITH TIME ZONE | not null | |

**`vehiculos`** — un vehículo conocido por el sistema, por alta explícita o por primera entrada.

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `id` | UUID | PK | |
| `placa` | VARCHAR(10) | not null, unique | Siempre normalizada: mayúsculas, sin espacios ni guiones, `^[A-Z0-9]{3,10}$` |
| `tipo` | VARCHAR(20) | not null, check in (`OFICIAL`, `RESIDENTE`, `NO_RESIDENTE`) | Texto restringido, no enum de base de datos, para poder añadir tipos con una migración simple |
| `estancia_abierta_id` | UUID | null, unique, FK → `estancias.id` | `null` = fuera; con valor = dentro. Es la garantía a nivel de base de datos de una sola estancia abierta por vehículo |
| `created_at`, `updated_at` | TIMESTAMP WITH TIME ZONE | not null | |

**`estancias`** — una visita: abierta mientras `salida` es `null`, cerrada e inmutable después.

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `id` | UUID | PK | |
| `vehiculo_id` | UUID | not null, FK → `vehiculos.id` | |
| `entrada` | TIMESTAMP WITH TIME ZONE | not null | Asignada por el servidor |
| `salida` | TIMESTAMP WITH TIME ZONE | null | Asignada por el servidor al registrar la salida |
| `minutos` | INT | null | Minutos completos: `Duration.between(entrada, salida).toMinutes()`; segundos truncados |
| `importe` | DECIMAL(12,2) | null | Importe generado por la estancia con la tarifa del tipo vigente al salir |
| `periodo_id` | UUID | null, FK → `periodos.id` | Se fija al cerrar: periodo activo en el momento de la salida. `null` en estancias abiertas |
| `created_at`, `updated_at` | TIMESTAMP WITH TIME ZONE | not null | |

**`acumulados_residentes`** — tiempo e importe acumulados de un residente en un periodo. Una fila por (vehículo, periodo).

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `id` | UUID | PK | |
| `vehiculo_id` | UUID | not null, FK → `vehiculos.id` | |
| `periodo_id` | UUID | not null, FK → `periodos.id` | |
| `minutos` | INT | not null, default 0 | Suma de minutos de las estancias cerradas del residente en el periodo |
| `importe` | DECIMAL(12,2) | not null, default 0 | Suma de importes de esas estancias |
| `created_at`, `updated_at` | TIMESTAMP WITH TIME ZONE | not null | |

Unique `(vehiculo_id, periodo_id)`. "Reiniciar acumulados" no borra nada: el periodo nuevo simplemente
no tiene filas todavía.

### Relationships

- `vehiculos —(1:N)→ estancias` por `estancias.vehiculo_id`. Sin borrado en cascada: v1 no borra vehículos.
- `vehiculos —(0..1:1)→ estancias` por `vehiculos.estancia_abierta_id` (la estancia abierta actual). Se pone a `null` al cerrar.
- `periodos —(1:N)→ estancias` por `estancias.periodo_id` (solo estancias cerradas).
- `vehiculos —(1:N)→ acumulados_residentes` y `periodos —(1:N)→ acumulados_residentes`.
- Ninguna relación borra en cascada: v1 no expone ninguna operación de borrado.

### Indexes

| Table | Index | Why |
|---|---|---|
| `vehiculos` | `uq_vehiculos_placa (placa)` | Búsqueda por placa en entrada, salida, alta y detalle; unicidad real |
| `vehiculos` | `uq_vehiculos_estancia_abierta (estancia_abierta_id)` | Una estancia solo puede ser "la abierta" de un vehículo |
| `periodos` | `uq_periodos_activo (activo)` | H2 admite varios `NULL` en un índice único, así que a lo sumo una fila tiene `TRUE`: un solo periodo activo |
| `estancias` | `idx_estancias_vehiculo_id (vehiculo_id)` | FK |
| `estancias` | `idx_estancias_periodo_id (periodo_id)` | FK; consultas por periodo |
| `estancias` | `idx_estancias_vehiculo_entrada (vehiculo_id, entrada DESC)` | Historial del detalle, más recientes primero |
| `acumulados_residentes` | `uq_acumulados_vehiculo_periodo (vehiculo_id, periodo_id)` | Una fila por residente y periodo; sirve al informe |
| `acumulados_residentes` | `idx_acumulados_periodo_id (periodo_id)` | FK; el informe filtra por periodo activo |

**Decisión sobre H2 y unicidad condicional.** H2 no tiene índices únicos parciales. Se eligió modelar
las dos invariantes con columnas anulables únicas en lugar de una comprobación solo en servicio:
`periodos.activo` (`TRUE` o `NULL`) y `vehiculos.estancia_abierta_id`. Así la base de datos rechaza el
estado inválido aunque el servicio tenga un defecto; el bloqueo pesimista del servicio sigue siendo la
primera línea y la prueba del paso 6 lo confirma.

### Migrations

Flyway, archivos SQL escritos a mano en `backend/src/main/resources/db/migration/`, convención

## 5. API Design

### Conventions

- **Base path:** `/neo`. Las rutas son el contrato literal del enunciado y se conservan tal cual: sin
  prefijo `/v1` y sin renombrar. (Desviación consciente de la regla de versionado en la ruta de
  `api-design.md`: gana el enunciado.) `GET /actuator/health` y la documentación (`/v3/api-docs`,
  `/swagger-ui.html`) quedan fuera de `/neo`.
- **Respuesta de éxito:** el recurso directamente, sin envoltorio `{ data }`. Las listas usan
  `PageResponse<T>`: `{ "content": [], "page": 0, "size": 10, "totalElements": 0, "totalPages": 0 }`.
- **Respuesta de error — una sola forma, siempre:** RFC 9457 `ProblemDetail`
  (`Content-Type: application/problem+json`) con dos propiedades de extensión: `code` (cadena estable
  para máquinas) y `errors` (lista de `{ "field", "message" }`, presente solo en errores de validación).
  Nunca un 200 con un error dentro.

  ```json
  {
    "type": "about:blank",
    "title": "Conflict",
    "status": 409,
    "detail": "El vehículo ABC123 ya se encuentra dentro",
    "instance": "/neo/estancias/entrada",
    "code": "VEHICULO_YA_DENTRO"
  }
  ```

  ```json
  {
    "type": "about:blank",
    "title": "Bad Request",
    "status": 400,
    "detail": "La solicitud contiene datos inválidos",
    "instance": "/neo/vehiculos/oficiales",
    "code": "VALIDACION",
    "errors": [{ "field": "placa", "message": "La placa debe tener de 3 a 10 letras o dígitos" }]
  }
  ```

  Los dos bloques anteriores ilustran la forma; las pruebas afirman campo por campo (`status`, `code`,
  `errors[0].field`), nunca el cuerpo completo byte a byte, porque `title` y `type` los redacta Spring.

- **Error codes** (conjunto cerrado; el frontend ramifica por `code`, nunca por `detail`):

  | `code` | HTTP | Cuándo |
  |---|---|---|
  | `VALIDACION` | 400 | Cuerpo ausente o mal formado, `placa` vacía, o placa que tras normalizar no cumple `^[A-Z0-9]{3,10}$` |
  | `PARAMETRO_INVALIDO` | 400 | `sort` fuera de la lista blanca, dirección distinta de `asc`/`desc`, `page` < 0 o `size` < 1 |
  | `VEHICULO_NO_ENCONTRADO` | 404 | Salida, detalle o historial de una placa que no existe |
  | `VEHICULO_YA_REGISTRADO` | 409 | Alta de una placa que ya es `OFICIAL` o `RESIDENTE`, o alta como no residente de una placa existente |
  | `VEHICULO_YA_DENTRO` | 409 | Entrada de una placa con estancia abierta |
  | `VEHICULO_NO_DENTRO` | 409 | Salida de una placa sin estancia abierta |
  | `ERROR_INTERNO` | 500 | Cualquier excepción no prevista; sin traza en el cuerpo |

- **Validation:** Bean Validation (`jakarta.validation`) en los records de `web` — `PlacaRequest` lleva
  `@NotBlank @Size(min = 3, max = 20)` sobre `placa` (el máximo es holgado porque el valor crudo puede
  traer espacios y guiones) — y después el value object `domain.Placa` normaliza y valida el formato
  estricto. Ambas fallas producen 400 `VALIDACION` con `errors[0].field = "placa"`.
- **Normalización de placa:** mayúsculas, se eliminan espacios y guiones, y el resultado debe cumplir
  `^[A-Z0-9]{3,10}$`. `abc-123 d` → `ABC123D`. Aplica a cuerpos, a `{placa}` en la ruta y al filtro.
- **Pagination:** por desplazamiento (`page` base 0, `size`), adecuada a un listado administrativo con
  páginas numeradas y a `MatPaginator`. `size` por defecto 10; un `size` mayor que 100 se recorta a 100
  (no es error). `page` por defecto 0.
- **Sorting:** `sort=<campo>,<asc|desc>`; lista blanca `placa`, `tipo`, `createdAt`; por defecto
  `placa,asc`. Un campo fuera de la lista devuelve 400 `PARAMETRO_INVALIDO`, no se ignora.
- **Filtering:** `placa` — coincidencia parcial ("contiene") sobre la placa normalizada; el valor del
  filtro se normaliza igual que una placa pero sin exigir longitud mínima.
- **Timestamps:** ISO-8601 con desplazamiento, zona `America/Mexico_City`
  (`2026-09-07T08:00:00-06:00`). Todos los asigna el servidor con el `Clock` inyectado.
- **Importes:** número JSON con 2 decimales (`BigDecimal`, `setScale(2, RoundingMode.HALF_UP)`).
- **Idempotency:** no hay cabecera `Idempotency-Key`. La protección contra dobles envíos es el propio
  modelo: una segunda entrada o una segunda salida responde 409.
- **Rate limits:** ninguno; herramienta local sin exposición pública.
- **Concurrencia:** entrada y salida se ejecutan en una transacción que bloquea la fila del vehículo
  con `@Lock(LockModeType.PESSIMISTIC_WRITE)`.

### Critical endpoints — full detail

#### `POST /neo/vehiculos/{oficiales|residentes|no-residentes}`

- **Request:** `PlacaRequest`.
- **201:** `VehiculoResponse` + cabecera `Location: /neo/vehiculos/{placa}` (placa normalizada).
- **Regla de alta y reclasificación** (de `Requerimientos.md`, "Vehículos no registrados"):

  | Estado actual de la placa | Alta como OFICIAL | Alta como RESIDENTE | Alta como NO_RESIDENTE |
  |---|---|---|---|
  | No existe | 201 crea | 201 crea | 201 crea |
  | `NO_RESIDENTE` | 201 reclasifica | 201 reclasifica | 409 `VEHICULO_YA_REGISTRADO` |
  | `OFICIAL` | 409 | 409 | 409 |
  | `RESIDENTE` | 409 | 409 | 409 |

- **Reclasificar** actualiza `tipo` y `updated_at` del mismo registro; no toca estancias ni cobros ya
  cerrados. Si el vehículo está dentro, la estancia abierta se cobrará al salir con el tipo nuevo.
- **Errores:** 400 `VALIDACION` · 409 `VEHICULO_YA_REGISTRADO`.
- **Efectos:** una fila insertada o actualizada en `vehiculos`. Una línea de log `evento=vehiculo_alta`.

#### `POST /neo/estancias/entrada`

- **Request:** `PlacaRequest`. **201:** `EstanciaResponse` con `salida`, `minutos`, `importe` y
  `periodoId` en `null`.
- **Flujo, en una transacción:** normalizar placa → buscar el vehículo **con bloqueo pesimista** → si
  no existe, crearlo como `NO_RESIDENTE` → si `estancia_abierta_id` no es `null`, 409
  `VEHICULO_YA_DENTRO` → insertar estancia con `entrada = ahora` → apuntar
  `vehiculos.estancia_abierta_id` a ella.
- **Errores:** 400 `VALIDACION` · 409 `VEHICULO_YA_DENTRO`.
- **Efectos:** 1 fila en `estancias`; 0 o 1 fila nueva en `vehiculos`; `evento=entrada`.

#### `POST /neo/estancias/salida`

- **Request:** `PlacaRequest`. **200:** `EstanciaResponse` completa.
- **Flujo, en una transacción:** normalizar placa → buscar el vehículo con bloqueo pesimista → si no
  existe, 404 `VEHICULO_NO_ENCONTRADO` → si `estancia_abierta_id` es `null`, 409 `VEHICULO_NO_DENTRO` →
  `minutos = Duration.between(entrada, ahora).toMinutes()` → `importe =
  calculadoraCobro.calcular(tipo, minutos)` → cerrar la estancia con `salida`, `minutos`, `importe` y
  `periodo_id` = periodo activo → `vehiculos.estancia_abierta_id = null` → si la estrategia del tipo
  declara `MomentoCobro.INFORME_MENSUAL`, sumar `minutos` e `importe` a la fila
  `(vehiculo, periodo activo)` de `acumulados_residentes`, creándola si no existe.
- **Cálculo** (tarifas de `acceso.tarifas.*` en `application.yml`):

  | Tipo | Importe | `momentoCobro` |
  |---|---|---|
  | `OFICIAL` | `0.00` | `NINGUNO` |
  | `RESIDENTE` | `minutos × 0.05` | `INFORME_MENSUAL` |
  | `NO_RESIDENTE` | `minutos × 0.50` | `AL_SALIR` |

  Casos de referencia: 0 s → 0 min → 0.00 · 59 s → 0 min → 0.00 · 10 min 5 s → 10 min · residente 11
  min → 0.55 · no residente 11 min → 5.50 · oficial cualquier duración → 0.00.
- **Errores:** 400 `VALIDACION` · 404 `VEHICULO_NO_ENCONTRADO` · 409 `VEHICULO_NO_DENTRO`.
- **Efectos:** 1 estancia actualizada, 1 vehículo actualizado, 0 o 1 acumulado insertado o
  actualizado; `evento=salida`.

#### `GET /neo/residentes/pagos`

- **Negociación por `Accept`** (dos métodos de controlador con `produces` distintos):
  - `application/json` (también el valor por defecto sin `Accept` o con `*/*`) → 200 `InformePagosResponse`.
  - `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` → 200 con el `.xlsx` y
    `Content-Disposition: attachment; filename="informe-pagos-<yyyy-MM>.xlsx"`, donde `<yyyy-MM>` es
    el mes de `periodo.inicio` en la zona `America/Mexico_City`.
- **Contenido:** una fila por cada vehículo de tipo `RESIDENTE`, ordenadas por placa ascendente, con
  el acumulado del **periodo activo** (0 minutos y 0.00 si no tiene fila). `totalMinutos` y
  `totalImporte` son la suma de las filas.
- **Excel** (`InformeExcelWriter`, `XSSFWorkbook`): una hoja llamada `Pagos`; fila 1 = cabeceras
  `Placa`, `Minutos`, `Importe`; una fila por residente; última fila = `TOTAL`, suma de minutos, suma
  de importes. Minutos e importe son celdas numéricas.
- **Con la precarga de §4:** 3 filas (`RES001` 210 / 10.50, `RES002` 30 / 1.50, `RES003` 60 / 3.00),
  `totalMinutos` 300, `totalImporte` 15.00, archivo `informe-pagos-2026-09.xlsx`.
- **Errores:** ninguno de negocio. **Efectos:** ninguno (solo lectura).

#### `POST /neo/mes/iniciar`

- **Request:** sin cuerpo. **200:** `IniciarMesResponse`.
- **Flujo, en una transacción:** leer el periodo activo → fijar `fin = ahora` y `activo = NULL` →
  **hacer flush** (la restricción `uq_periodos_activo` impide dos `TRUE` a la vez) → insertar el
  periodo nuevo con `inicio = ahora` y `activo = TRUE`.
- **Consecuencias:** las estancias cerradas conservan su `periodo_id` (quedan archivadas); los
  acumulados del periodo nuevo empiezan en cero porque aún no hay filas; las estancias abiertas no se
  tocan y se contabilizarán en el periodo activo cuando registren la salida.
- **Efectos:** 1 periodo actualizado, 1 periodo insertado; `evento=mes_iniciado`.

#### `GET /neo/vehiculos`, `GET /neo/vehiculos/{placa}`, `GET /neo/vehiculos/{placa}/estancias`

- Listado: `?placa=&page=0&size=10&sort=placa,asc` → `PageResponse<VehiculoResumen>`. Paginación,
  orden y filtro se ejecutan en la base de datos (`Pageable`), nunca en memoria.
- Detalle: `VehiculoDetalleResponse`; 404 `VEHICULO_NO_ENCONTRADO` si la placa no existe; 400
  `VALIDACION` si la placa de la ruta no es normalizable.
- Historial: `?page=0&size=10` → `PageResponse<EstanciaResponse>` ordenado por `entrada` descendente
  (todas las estancias del vehículo, de todos los periodos); mismas reglas de `page` y `size`; 404 si
  la placa no existe.

## 6. Frontend Architecture

Aplicación Angular de página única, renderizada en cliente (`--ssr=false`): es una herramienta
interna sin superficie pública ni SEO, el caso en que `frontend-architecture.md` recomienda una SPA
con una API delgada. Todos los componentes son standalone; la detección de cambios es zoneless.

### Routes

| Route | Page | Data source | Auth |
|---|---|---|---|
| `/` | redirección a `/vehiculos` | — | público |
| `/vehiculos` | `VehiculosLista` | `GET /neo/vehiculos` | público |
| `/vehiculos/:placa` | `VehiculoDetalle` | `GET /neo/vehiculos/{placa}` y `GET /neo/vehiculos/{placa}/estancias` | público |
| `/operacion` | `Operacion` | `POST` de alta, entrada, salida e iniciar mes | público |
| `/reporte` | `Reporte` | `GET /neo/residentes/pagos` (JSON y blob `.xlsx`) | público |
| `**` | `NoEncontrado` | estático | público |

Este es el manifiesto de rutas; no hay rutas "por decidir".

### Rendering strategy

Todas las rutas son de cliente. Cada página se carga de forma diferida con `loadComponent` en
`app.routes.ts`; el shell (`layout/shell/shell.ts`) se carga con la aplicación. En desarrollo,
`ng serve` reenvía `/neo` y `/actuator` a `http://localhost:8080` mediante `proxy.conf.json`, de modo
que el frontend usa rutas relativas y no hay CORS que configurar. No hay caché de datos: cada
navegación vuelve a pedir.

### Component hierarchy

```
App (app.ts)
└── Shell (mat-sidenav-container + mat-toolbar; nav: Vehículos · Operación · Reporte)
    └── <router-outlet>
        ├── VehiculosLista
        │   ├── campo de filtro por placa (FormControl, debounce 300 ms)
        │   ├── mat-table [matSort] → columnas Placa · Tipo · Estado · Alta · acción "Ver detalle"
        │   │   └── EstadoChip (tipo) · EstadoChip (dentro/fuera)
        │   ├── Loading | EmptyState | bloque de error con "Reintentar"
        │   └── mat-paginator (server-side)
        ├── VehiculoDetalle
        │   ├── cabecera: placa (.placa) + EstadoChip tipo + EstadoChip dentro/fuera
        │   ├── tarjeta "Acumulado del periodo" (solo residentes)
        │   ├── tarjeta "Estancia abierta" (solo si está dentro)
        │   ├── mat-table de estancias + mat-paginator
        │   └── Loading | EmptyState | estado "no encontrado"
        ├── Operacion
        │   ├── EntradaForm      (tarjeta, Reactive Form)
        │   ├── SalidaForm       (tarjeta, Reactive Form; muestra minutos e importe del resultado)
        │   ├── AltaForm         (tarjeta; placa + selector de tipo)
        │   └── IniciarMes       (botón → ConfirmarDialog → POST)
        ├── Reporte
        │   ├── cabecera con periodo y botón "Descargar Excel"
        │   ├── mat-table Placa · Minutos · Importe + fila de total
        │   └── Loading | EmptyState | bloque de error
        └── NoEncontrado
```

### State management

- **Estado de servidor:** vive en el componente de página como `signal`s (`datos`, `cargando`,
  `error`). Los servicios de `core/api/` devuelven `Observable` de `HttpClient`; el componente se
  suscribe y escribe en sus signals. No hay store global ni caché compartida: ningún dato cruza rutas.
- **Estado de URL:** la página, el tamaño, el orden y el filtro del listado viven en signals del
  componente; la placa del detalle viene del parámetro de ruta.
- **Formularios:** Reactive Forms (`FormBuilder` no anulable). El validador `placaValidator` aplica la
  misma normalización y la misma expresión `^[A-Z0-9]{3,10}$` que el backend; la directiva
  `appPlacaMayusculas` pasa a mayúsculas mientras se escribe.
- **Errores HTTP:** `problemDetailInterceptor` (funcional) lee `detail` del `ProblemDetail` y lo
  muestra en un `MatSnackBar`; vuelve a lanzar el error para que el componente pase a su estado de
  error. Si la respuesta no es un `ProblemDetail` (backend caído) muestra "No se pudo conectar con el
  servidor".
- **Deliberadamente fuera de estado global:** todo. No hay NgRx, ni servicios con estado, ni
  `localStorage`.

### Loading, empty, and error states

| Superficie | Cargando | Vacío | Error |
|---|---|---|---|
| Listado de vehículos | `Loading` (barra de progreso + `aria-busy`) sobre la tabla | `EmptyState`: "No hay vehículos" / con filtro: "Ningún vehículo coincide con «X»" + botón "Limpiar filtro" | Texto "No se pudo cargar el listado" + botón "Reintentar" |
| Detalle | `Loading` | Historial sin filas: "Este vehículo aún no tiene estancias" | 404 → bloque "Vehículo no encontrado" con enlace a `/vehiculos`; otro error → "Reintentar" |
| Formularios de operación | Botón deshabilitado con indicador mientras se envía | — | `mat-error` por campo + snackbar con el `detail` del backend; el valor escrito se conserva |
| Reporte | `Loading` | "No hay residentes registrados" | "No se pudo cargar el informe" + "Reintentar" |

Todo estado de carga tiene su estado de error; ningún indicador puede quedarse girando tras un fallo.

## 9. BUILD ORDER

**Esta es la sección para la que existe todo el blueprint.** Lo anterior es contexto; esto es el
conjunto de instrucciones. Un constructor que siga §9 al pie de la letra y se detenga cuando cada
puerta quede en verde entrega el proyecto.

**Antes del paso 1** se ejecuta una sola vez el bloque Bootstrap de §10: crea el repositorio y la
rama, copia `workspace/` a la raíz, genera `backend/` y `frontend/` con sus scaffolders y hace el
primer commit.

### Reglas de un paso

1. **Un paso, una sentada.** Cada paso tiene como máximo 5 entradas de archivos y 6 criterios.
2. **Cuatro campos siempre, en este orden:** `Do` → `Done when` → `Verify` → `Checkpoint`.
3. **`Done when` es observable y decidible por una máquina**, en forma EARS: **WHEN** `<disparador>`
   **THE SYSTEM SHALL** `<respuesta observable>`.
4. **`Verify` es shell literal** (Git Bash). **Cada línea se ejecuta en su propio shell desde la raíz
   del proyecto**; por eso las que entran a un subdirectorio van entre paréntesis (`(cd backend &&
   ...)`), lo que además permite pegar el bloque entero. Cada línea sale con 0 cuando el paso está
   bien; donde el resultado correcto es un código distinto de 0 (un `grep` sin coincidencias), la línea
   afirma el código exacto (`...; test $? -eq 1`).
5. **Un paso no está hecho hasta que pasan sus comandos y siguen pasando los de los pasos anteriores.**
   Las puertas completas (`./mvnw verify`, `npm run test:ci`) se repiten en cada paso justamente para eso.
6. **`Checkpoint` es un bloque de shell:** un commit con mensaje Conventional Commits y la línea
   `Co-Authored-By`, y la etiqueta `step-NN-<slug>`. Esa etiqueta es el punto de retorno del paso
   siguiente: si un paso sale mal, `git reset --hard <etiqueta anterior>` y se reintenta; nunca se
   depura hacia adelante sobre un checkpoint roto. Las afirmaciones sobre estado confirmado (archivos
   rastreados) van dentro del Checkpoint, después del commit, nunca en `Verify`.
7. **Nunca saltar pasos.** Si un paso se bloquea, detenerse y reportar.
8. **Ningún paso introduce una exigencia que rompa una puerta anterior.** Spotless llega en el paso 2
   junto con el formateo del código existente; JaCoCo llega en el paso 8, que es el que termina los
   paquetes que mide; Prettier llega en el paso 9 junto con `npm run format`.
9. **Nunca hacer `git push`**, crear el fork ni abrir el pull request: son pasos manuales de la
   persona (paso 15, `docs/PR.md`).
10. **Obligatorio antes que extras.** Si el tiempo aprieta, lo marcado como "extra recomendado" en el
    enunciado (filtro, paginación y orden, pruebas de frontend) se recorta dentro del paso; los
    endpoints y pantallas obligatorios, no.

**Formato del mensaje de commit.** `<tipo>(<ámbito>): <resumen> [<id de tarea>]` — Conventional Commits
por petición de la usuaria, con el id de tarea al final para que el protocolo de reanudación de
`tasks.json` pueda localizarlo. Los mensajes van sin acentos para evitar problemas de codificación en
la consola de Windows.

**Ramas.** Todo se construye sobre `feature/xochitlgr`. Si se prefiere una rama por épica, se crea
desde `feature/xochitlgr` y se integra de vuelta con `git merge --no-ff`; las etiquetas de checkpoint
se crean igual.

### Un paso, una unidad — la regla de conteo

> **Un paso de §9 = una tarea de `tasks.json` = un bloque de tarea en un archivo de épica.**

Este blueprint tiene **15 pasos**, 15 tareas y 15 bloques de tarea. Los agrupan **4 épicas**, por
decisión explícita de la usuaria, siguiendo las costuras reales del trabajo: `01-base` (paso 1),
`02-backend` (pasos 2–8), `03-frontend` (pasos 9–13) y `04-calidad-entrega` (pasos 14–15).

**Desviación declarada:** la regla general de The Architect pide de 5 a 9 pasos por épica (para 15
pasos, 2 o 3 épicas). Aquí `01-base` y `04-calidad-entrega` quedan por debajo de 5 porque la usuaria
alimentará cada épica a Spec Kit como una feature independiente y quiere que la base del repositorio
y la entrega sean unidades propias. El número de pasos, el orden y las dependencias no cambian.

Las dependencias de la tabla son restricciones reales, no orden narrativo: el backend (2–8) y el
frontend (9–13) solo dependen de Bootstrap y entre sí no comparten archivos, así que pueden avanzar
en paralelo; los pasos 10 a 13 dependen solo del 9.

#### Step 4 — Implementar altas de vehículo y manejo de errores

**Tarea:** `E2-T3` · **Épica:** `02-backend` · **Prioridad:** p0 · **Depends on:** paso 3 (`E2-T2`)

**Goal** — Los tres endpoints de alta crean o reclasifican vehículos, y todo error sale como `ProblemDetail` con `code` y `errors`.

**Do**

Primera rebanada vertical completa: caso de uso → puerto → adaptador JPA → controlador → manejo de
errores. Lo que se decida aquí (puerto de transacción, manejador de errores, estilo de pruebas) lo
reutilizan todos los pasos siguientes del backend.

**Aplicación** (`application`, sin Spring):

- `puerto/VehiculoRepositorio` — `Optional<Vehiculo> buscarPorPlaca(Placa)`, `Vehiculo guardar(Vehiculo)`,
  `long contar()`.
- `puerto/Transaccion` — `<T> T ejecutar(Supplier<T> accion)`. Es la frontera transaccional de los
  casos de uso sin depender de `@Transactional`.
- `RegistrarVehiculo` — `Vehiculo ejecutar(String placaCruda, TipoVehiculo tipo)`. Dentro de
  `transaccion.ejecutar`: normaliza con `Placa.de`; si la placa no existe, crea el vehículo; si existe
  como `NO_RESIDENTE` y el tipo pedido es `OFICIAL` o `RESIDENTE`, lo reclasifica conservando el `id`;
  en cualquier otro caso lanza `VehiculoYaRegistradoException`. Usa el `Clock` inyectado para
  `createdAt`/`updatedAt` y `UUID.randomUUID()` para el id.

**Infraestructura**:

- `persistencia/VehiculoEntity` — `@Entity @Table(name = "vehiculos")` con los campos del modelo de
  datos (`estanciaAbiertaId` como columna `UUID` simple, sin relación mapeada), `VehiculoJpaRepository`
  (`JpaRepository<VehiculoEntity, UUID>` con `findByPlaca`), `VehiculoRepositorioJpa` (adaptador que
  implementa el puerto y convierte entidad ↔ dominio) y `TransaccionSpring` (implementa `Transaccion`
  con `TransactionTemplate`).
- `config/CasosDeUsoConfig` — `@Configuration` con un `@Bean` por caso de uso; los casos de uso no
  llevan anotaciones de Spring.

**Web**:

- `PlacaRequest` — `record PlacaRequest(@NotBlank @Size(min = 3, max = 20) String placa)`.
- `VehiculoResponse` — `record` con `id`, `placa`, `tipo`, `dentro`, `createdAt`.
- `VehiculosController` — `@RestController @RequestMapping("/neo/vehiculos")` con `POST /oficiales`,
  `POST /residentes` y `POST /no-residentes`; cada uno responde
  `ResponseEntity.created(URI.create("/neo/vehiculos/" + placa)).body(...)`.

#### Step 5 — Registrar entradas y salidas con cálculo de cobro

**Tarea:** `E2-T4` · **Épica:** `02-backend` · **Prioridad:** p0 · **Depends on:** paso 4 (`E2-T3`)

**Goal** — Entrada y salida funcionan de extremo a extremo con bloqueo pesimista, alta automática de no residentes, minutos truncados, importe por estrategia y acumulado de residentes.

**Do**

El núcleo del negocio. Entrada y salida corren cada una en una transacción que bloquea la fila del
vehículo, de modo que dos peticiones simultáneas no pueden abrir dos estancias para la misma placa.

**Aplicación**:

- Puertos nuevos: `EstanciaRepositorio` (`guardar`, `buscarPorId`), `PeriodoRepositorio`
  (`Periodo activo()`), `AcumuladoRepositorio` (`Optional<Acumulado> buscar(UUID vehiculoId, UUID
  periodoId)`, `guardar`). Añade a `VehiculoRepositorio` el método `Optional<Vehiculo>
  buscarPorPlacaParaActualizar(Placa)`.
- `RegistrarEntrada` — sigue el flujo del contrato: normalizar → buscar con bloqueo → crear como
  `NO_RESIDENTE` si no existe → si tiene estancia abierta, `VehiculoYaDentroException` → crear estancia
  con `entrada = OffsetDateTime.now(clock)` → apuntar `estanciaAbiertaId`.
- `RegistrarSalida` — normalizar → buscar con bloqueo → `VehiculoNoEncontradoException` si no existe →
  `VehiculoNoDentroException` si no tiene estancia abierta → `minutos = Estancia.minutosCompletos(...)`
  → `importe = calculadora.calcular(tipo, minutos)` → cerrar la estancia con `periodoId` del periodo
  activo → `estanciaAbiertaId = null` → **si `calculadora.momento(tipo) == MomentoCobro.INFORME_MENSUAL`**,
  sumar minutos e importe al acumulado `(vehículo, periodo activo)`, creándolo si no existe. La
  condición es sobre el momento de cobro que declara la estrategia, nunca sobre el tipo.

**Infraestructura**:

- Entidades `EstanciaEntity`, `PeriodoEntity`, `AcumuladoEntity` con sus repositorios Spring Data y
  adaptadores. Tipos Java: `UUID`, `OffsetDateTime`, `BigDecimal` con `@Column(precision = 12, scale =
  2)`, `Integer` para `minutos`, `Boolean` (envoltorio) para `activo`.
- En `VehiculoJpaRepository`: `@Lock(LockModeType.PESSIMISTIC_WRITE) @Query("select v from
  VehiculoEntity v where v.placa = :placa") Optional<VehiculoEntity> buscarParaActualizar(String placa)`.
- En `config/`: beans de `CobroOficial`, `CobroResidente` y `CobroNoResidente` construidos con
  `TarifasProperties`, el bean `CalculadoraCobro` con la lista de estrategias, y los beans de los dos
  casos de uso.

**Web**: `EstanciasController` (`POST /neo/estancias/entrada` → 201, `POST /neo/estancias/salida` →
200) y `EstanciaResponse` con `id`, `placa`, `tipo`, `entrada`, `salida`, `minutos`, `importe`,
`momentoCobro`, `periodoId`.

**Pruebas**:

- `soporte/RelojDePrueba` — subclase de `Clock` con instante ajustable (`fijar(Instant)`,
  `avanzar(Duration)`), zona `America/Mexico_City`, registrada con un `@TestConfiguration` que la

#### Step 6 — Implementar inicio de mes y archivo de periodos

**Tarea:** `E2-T5` · **Épica:** `02-backend` · **Prioridad:** p0 · **Depends on:** paso 5 (`E2-T4`)

**Goal** — `POST /neo/mes/iniciar` cierra el periodo activo y abre uno nuevo sin borrar estancias ni acumulados.

**Do**

"Reiniciar el mes" no borra nada: cierra el periodo activo y abre uno nuevo. Los acumulados del
periodo nuevo empiezan en cero porque todavía no existe ninguna fila para él, y las estancias
cerradas conservan el `periodo_id` con el que se archivaron.

- `application/IniciarMes` — dentro de `transaccion.ejecutar`: obtiene el periodo activo, lo cierra con
  `fin = OffsetDateTime.now(clock)`, y abre uno nuevo con `inicio` igual a ese mismo instante. Devuelve
  un resultado con `periodoAnterior` y `periodoActual`. Añade a `PeriodoRepositorio` los métodos
  `cerrar(Periodo)` y `abrir(Periodo)`.
- Adaptador de periodos — `cerrar` pone `activo = null` y `fin`, y **hace `saveAndFlush`** antes de que
  `abrir` inserte la fila con `activo = true`: la restricción `uq_periodos_activo` no admite dos `TRUE`
  ni siquiera dentro de la misma transacción. Registra el bean del caso de uso en
  `config/CasosDeUsoConfig`.
- `web/MesController` — `POST /neo/mes/iniciar` → 200 con `IniciarMesResponse(periodoAnterior,
  periodoActual)`; `PeriodoResponse` lleva `id`, `inicio`, `fin`.
- Log: `evento=mes_iniciado periodo_anterior=<id> periodo_actual=<id>`.

Pruebas:

- `IniciarMesTest` — unitaria con Mockito: se cierra el activo con la hora del reloj y se abre el nuevo.
- `MesIntegracionTest` — `@SpringBootTest` + `@AutoConfigureMockMvc` + `@Transactional` con
  `RelojDePrueba`: (a) tras iniciar mes queda exactamente 1 fila con `activo = true`; (b) el número de
  filas de `estancias` y de `acumulados_residentes` no cambia y las estancias cerradas conservan su
  `periodo_id`; (c) `RES001` registra entrada y salida después del cambio y aparece una fila nueva de
  acumulado para el periodo nuevo con solo esos minutos, mientras la fila del periodo anterior sigue
  con 210 minutos; (d) `OFI002`, que estaba dentro desde antes, sale después del cambio y su estancia
  queda con el `periodo_id` del periodo nuevo; (e) insertar con `JdbcTemplate` una segunda fila con

### Bootstrap

Se ejecuta una vez, antes del paso 1, **desde la raíz del proyecto** (`C:/dev/Gestion-Acceso-Vehicular`).
Es no interactivo y se puede volver a ejecutar: una segunda ejecución sale con 0 y no revierte nada.

```bash
set -euo pipefail
export NG_CLI_ANALYTICS=false   # evita la pregunta de telemetria del CLI de Angular

# order matters: repo init → upstream/main → rama de trabajo → copia de workspace (ignore file +
#                atributos de fin de linea) → scaffolds → prueba de toolchain → primer commit

# 1. Repositorio, remoto y ramas (cada linea es idempotente)
git rev-parse --git-dir >/dev/null 2>&1 || git init -q -b main
git remote get-url upstream >/dev/null 2>&1 || git remote add upstream https://github.com/VictorMC96/Full-Stack-Prueba-tecnica-Neology.git
git fetch -q upstream
git rev-parse --verify -q main >/dev/null || git checkout -q -B main upstream/main
git rev-parse --verify -q feature/xochitlgr >/dev/null || git checkout -q -b feature/xochitlgr main
git checkout -q feature/xochitlgr

# 2. Espacio de trabajo del agente + .gitignore/.gitattributes/.editorconfig, ANTES del primer commit
[ -f CLAUDE.md ] || cp -R blueprints/gestion-acceso-vehicular/workspace/. .   # guardado: CLAUDE.md hace de marca; una segunda ejecucion no pisa archivos que Spec Kit o la persona hayan editado, y el guard sale con 0

# 3. Backend: Spring Initializr es el autor de backend/pom.xml
if [ ! -f backend/pom.xml ]; then
  curl -fsSL https://start.spring.io/starter.tgz \
    -d type=maven-project -d language=java -d bootVersion=4.1.1 -d javaVersion=21 \
    -d groupId=mx.neology -d artifactId=backend -d name=backend \
    -d packageName=mx.neology.acceso -d baseDir=backend \
    -d dependencies=web,data-jpa,h2,flyway,validation,actuator \
    -o backend.tgz
  tar -xzf backend.tgz
  rm -f backend.tgz
fi

# 4. Frontend: Angular CLI es el autor de frontend/package.json
if [ ! -f frontend/package.json ]; then
  npx -y @angular/cli@22.2.0 new frontend --directory frontend --style=scss --test-runner=karma \
    --routing --ssr=false --skip-git --package-manager=npm --defaults
fi

# 5. Prueba de toolchain: descarga Maven y dependencias, ejecuta la prueba que genero Initializr y compila el frontend
(cd backend && ./mvnw -q -B -ntp test)
(cd frontend && npm run build --silent)

# 6. Primer commit (los Checkpoints de la seccion 9 necesitan un commit al que apuntar)
git add -A
git update-index --chmod=+x backend/mvnw   # en Windows git no registra el bit de ejecucion; CI en Linux lo necesita
git diff --cached --quiet || git commit -q -m "chore: scaffold backend y frontend, workspace del blueprint" -m "Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>"
```

**Qué deja en disco.** La rama `feature/xochitlgr` creada desde `upstream/main`; los archivos de
`workspace/` en la raíz; `backend/` (proyecto Maven con `mx.neology.acceso.BackendApplication`, el
wrapper y una prueba `contextLoads`); `frontend/` (aplicación Angular standalone con SCSS y Karma, con
`node_modules/` instalado); y un primer commit con todo ello.

**Autoría de los manifiestos.** `backend/pom.xml` es de Spring Initializr y `frontend/package.json`
es del CLI de Angular. Este blueprint **no** emite esos archivos bajo `workspace/` — `ng new` rechaza
un directorio no vacío — y solo describe ediciones encima: los pasos 2 y 8 sobre el `pom.xml`, los
pasos 9 y 14 sobre el `package.json`.

**Identificador `web` en Initializr.** `web` es el id que documenta Spring Initializr; con Spring Boot
4 genera el starter `spring-boot-starter-webmvc`. La prueba de arranque del paso 2 lo confirma
haciendo peticiones HTTP reales.

**Seguridad de la segunda ejecución, línea por línea.** `git init`, `git remote add`, los dos
`git checkout -b` y los dos scaffolds están guardados por una comprobación que sale con 0 cuando lo
guardado ya existe. La copia de `workspace/` solo ocurre si `CLAUDE.md` no existe: ningún archivo de
`workspace/` se vuelve a escribir, y `backend/pom.xml` y `frontend/package.json` nunca están bajo
`workspace/`, así que la copia no puede revertir dependencias instaladas. `./mvnw test` y `npm run
build` simplemente se repiten. El commit final se omite si no hay nada preparado.

**Supuestos declarados sobre `upstream`.** (1) Su rama por defecto es `main`. (2) No contiene archivos
en las rutas que ya existen localmente sin rastrear (`Requerimientos.md`, `Requerimientos.txt`,
`.claude/`, `.specify/`, `blueprints/`) ni directorios `backend/` o `frontend/`; si los contuviera,
`git checkout -B main upstream/main` abortaría con "untracked working tree files would be
overwritten" y nombraría el archivo: se mueve ese archivo a un lado, se repite el bloque y se
reconcilia a mano.

**Si falla la red.** `curl -f` y `git fetch` fallan de inmediato con su propio mensaje; se repite el
bloque cuando haya conexión. No hay estado parcial peligroso: cada scaffold se reintenta mientras su
manifiesto no exista (si `ng new` dejó un `frontend/` a medias sin `package.json`, bórralo con
`rm -rf frontend` antes de repetir).

### Critical flows to cover E2E

No hay suite E2E de navegador (non-goal de §1). Los tres flujos que más cuestan si se rompen están
cubiertos a nivel de integración de backend y de componente de frontend:

1. Entrada → salida de un no residente con cobro al salir (`EstanciasIntegracionTest`, `salida-form.spec.ts`).
2. Salida de un residente → acumulado → informe de pagos en JSON y Excel (`EstanciasIntegracionTest`, `InformeIntegracionTest`, `reporte.spec.ts`).
3. Inicio de mes → acumulados en cero con historial intacto (`MesIntegracionTest`, `iniciar-mes.spec.ts`).

### Test data

La base de pruebas es la misma H2 en memoria, creada por Flyway con `V1__esquema.sql` y
`V2__datos_iniciales.sql` al levantar el contexto. No hay servicio externo que aprovisionar. Las
pruebas de integración que escriben llevan `@Transactional` y se revierten, de modo que la precarga
(6 vehículos, 7 estancias, 3 acumulados) queda intacta para las demás y el orden de ejecución no
importa. `ArranqueHttpTest` usa HTTP real y por eso es de solo lectura. El tiempo se controla con
`Clock.fixed` en unitarias y con `soporte/RelojDePrueba` en integración. En el frontend los datos de
prueba son objetos literales dentro de cada spec, servidos con `HttpTestingController`.

### What is deliberately not tested

- E2E de navegador y pruebas visuales (non-goal).
- Concurrencia real con hilos sobre entrada/salida: la garantía es el bloqueo pesimista más la
  restricción única; una prueba con hilos sobre H2 sería frágil.
- Comportamiento de librerías: Spring Data, Flyway, Material, POI más allá del archivo que genera
  este proyecto.
- Estilos y copia exacta en pruebas funcionales, salvo los textos de estado que nombran los criterios.
- La ejecución del workflow de CI (nadie hace push durante la construcción); se valida su contenido.

**Target: WCAG 2.2 Level AA.** El personal usa la herramienta todo el turno: operar con teclado es

de los pasos 9 a 14, no en una lista pendiente.

### Baseline requirements

| Requirement | Rule |
|---|---|
| Semantic HTML | Landmarks `<nav>` y `<main>` en el shell, un `h1` por página, `h2` para títulos de tarjeta, `lang="es"` en `index.html`, `<title>` descriptivo |

## 19. Agent Workspace

El proyecto se entrega con su propia configuración para agentes. En modo bundle son **archivos
reales** bajo `blueprints/gestion-acceso-vehicular/workspace/`, con la misma disposición que la raíz
del proyecto; los bloques de esta sección reproducen su contenido exacto para que quien lea el
blueprint vea lo mismo que se copia.

```
blueprints/gestion-acceso-vehicular/workspace/
├── CLAUDE.md                                   # §19.1
├── AGENTS.md                                   # §19.2
├── .gitignore                                  # §19.6
├── .gitattributes                              # §19.6
├── .editorconfig                               # §19.6
└── .claude/
    ├── settings.json                           # §19.3
    ├── skills/verificar-backend/SKILL.md       # §19.4
    ├── skills/verificar-frontend/SKILL.md      # §19.4
    ├── skills/agregar-tipo-vehiculo/SKILL.md   # §19.4
    ├── rules/backend.md                        # §19.5
    └── rules/frontend.md                       # §19.5
```

**La copia es segura de repetir.** La hace el bloque Bootstrap de §10 con esta línea:

```bash
[ -f CLAUDE.md ] || cp -R blueprints/gestion-acceso-vehicular/workspace/. .   # guardado: CLAUDE.md hace de marca; una segunda ejecucion no pisa archivos que Spec Kit o la persona hayan editado, y el guard sale con 0
```

Es la forma "puerta con marca": si `CLAUDE.md` ya existe, la copia no ocurre y la línea sale con 0 (el
`[ -f ... ]` verdadero cortocircuita el `||`), igual en GNU y en BSD. **Archivos que nunca se
sobrescriben en una segunda ejecución:** todos los de `workspace/` —en particular `CLAUDE.md`, que el
script de contexto de Spec Kit puede editar— y, por construcción, `backend/pom.xml`,
`frontend/package.json` y `frontend/package-lock.json`, que no están bajo `workspace/`. **Nada de
`workspace/` cae dentro de `backend/` ni de `frontend/`.** La copia convive con lo que ya hay en
`.claude/`: las skills `speckit-*` existentes no se tocan.

**No se emite `.claude/commands/`.** Los flujos repetibles del proyecto son skills (§19.4), que se
activan por intención.

**Conformidad con las puertas del propio proyecto.** Ningún formateador del proyecto alcanza estos
archivos: Spotless solo mira `backend/src/**/*.java` y Prettier solo `frontend/src/**/*.{ts,html,scss}`.
Aun así se escriben con el estilo de `.editorconfig` (UTF-8, LF, 2 espacios, salto de línea final).

## Architecture

`infrastructure/persistencia/` → H2. Los errores vuelven como `ProblemDetail` desde
`web/ApiExceptionHandler` y el frontend los muestra con `core/interceptores/problem-detail.interceptor.ts`.

## Code rules

1. **Sin `if`/`switch` sobre `TipoVehiculo`** en casos de uso ni controladores: el cobro y el momento de
   cobro se piden a `CalculadoraCobro`.
2. **Sin Lombok.** `record` para DTOs y value objects.
3. **Dinero:** `BigDecimal` con `setScale(2, RoundingMode.HALF_UP)`; columnas `DECIMAL(12,2)`.
   Minutos: `Duration.toMinutes()` (trunca segundos).
4. **Tiempo:** toda fecha sale de `OffsetDateTime.now(clock)` con el `Clock` inyectado. Prohibido
   `now()` sin reloj y prohibido aceptar fechas del cliente.
5. **Placa:** siempre normalizada (mayúsculas, sin espacios ni guiones) y validada con
   `^[A-Z0-9]{3,10}$` antes de tocar la base de datos.
6. **Errores:** solo `ProblemDetail` con `code`; nunca un 200 con error dentro ni una traza al cliente.
7. **Listas:** paginación, orden y filtro en la consulta SQL; tamaño máximo 100.
8. **Pruebas backend:** `@MockitoBean` (nunca `@MockBean`); JSON con `jsonPath`; las pruebas que
   escriben llevan `@Transactional` para no contaminar la precarga.
9. **Frontend:** componentes standalone, signals, `@if`/`@for`, Reactive Forms; cada página con un
   solo `h1` y con estados de carga, vacío y error.
10. **Pruebas frontend:** `await fixture.whenStable()`; sin `fakeAsync` (la app es zoneless).
11. **Sin `innerHTML`** y sin colores hexadecimales en archivos de componentes.
12. **Commits:** Conventional Commits + `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`.

# Backend — convenciones

## Capas (`mx.neology.acceso`)

- `domain` y `application` son Java puro: ni `org.springframework`, ni `jakarta.persistence`, ni POI.
  Los casos de uso son clases sin anotaciones; se registran como beans en
  `infrastructure/config/CasosDeUsoConfig`.
- La frontera transaccional es el puerto `application.puerto.Transaccion`
  (`transaccion.ejecutar(() -> ...)`), implementado con `TransactionTemplate`. No uses
  `@Transactional` en casos de uso.
- `web` solo habla con casos de uso. Una entidad JPA nunca sale de `infrastructure.persistencia`;
  una respuesta HTTP siempre es un `record` de `web`.
- Añadir un tipo de vehículo = constante en `TipoVehiculo` + una clase `EstrategiaCobro` + su bean +
  su tarifa en `application.yml` + una migración que amplíe `ck_vehiculos_tipo`. Nada más cambia.

## Persistencia

- Flyway es el único dueño del esquema; `spring.jpa.hibernate.ddl-auto=validate`. Nunca edites una
  migración confirmada: crea `V<n+1>__<descripcion>.sql`.
- Tipos: `UUID` (generado con `UUID.randomUUID()`), `OffsetDateTime` para `TIMESTAMP WITH TIME ZONE`,
  `BigDecimal` con `@Column(precision = 12, scale = 2)`, `@Enumerated(EnumType.STRING)`.
- Entrada y salida leen el vehículo con `@Lock(LockModeType.PESSIMISTIC_WRITE)`.
- `periodos.activo` es `TRUE` o `NULL`, nunca `FALSE`. Al cerrar un periodo haz `saveAndFlush` antes
  de insertar el nuevo (`uq_periodos_activo`).
- Paginación, orden y filtro van en la consulta. `application` usa sus tipos `ConsultaPagina` y
  `Pagina<T>`; solo el adaptador conoce `Pageable`.

## Web y errores

- Rutas literales del enunciado bajo `/neo`; sin prefijo de versión.
- Todo error es un `ProblemDetail` construido en `ApiExceptionHandler` con la propiedad `code`
  (`VALIDACION`, `PARAMETRO_INVALIDO`, `VEHICULO_NO_ENCONTRADO`, `VEHICULO_YA_REGISTRADO`,
  `VEHICULO_YA_DENTRO`, `VEHICULO_NO_DENTRO`, `ERROR_INTERNO`) y, en validación, `errors`.
- Las excepciones de negocio extienden `ExcepcionDominio` y llevan su `codigo()`; los controladores
  no capturan excepciones.
- Log con SLF4J en formato `clave=valor` (`evento=salida placa=ABC123 minutos=10 importe=5.00`).

## Spring Boot 4

- Starter web: `spring-boot-starter-webmvc`. Conserva los starters de prueba que generó Initializr.
- Pruebas: `@MockitoBean`, nunca `@MockBean`. Jackson 3 vive en `tools.jackson.*`: afirma JSON con
  `jsonPath` y evita `ObjectMapper`.
